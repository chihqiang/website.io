用 Go 写一个完整的指标操作库：定义、注册、查询与计算

chihqiang 2026-11-14 约 52 分钟 20497 字

从指标定义到查询结果，用 Go 标准库实现一个可运行、可测试的指标操作库

前面几篇聊了统计平台和指标引擎的设计思路。这一篇把代码写完整：一个不依赖第三方库、可以直接 go test、go run 的指标操作库。

实现目标：

  • 指标可以注册、按名字请求；
  • 直接指标支持计数和求和，自带时间字段和过滤条件；
  • 间接指标声明依赖，按依赖顺序计算；
  • 一次请求混合直接指标和间接指标；
  • 后端可替换，测试不需要外部服务；
  • 完整示例跑出真实结果。

目录结构：

go.mod 只有模块声明，没有任何依赖：

go.mod

一、指标定义

先定义指标本身。直接指标负责“取数”，间接指标负责“计算”。

metric.go

两个关键设计：

  1. 时间字段属于指标，不属于请求。这样“下单量按创建时间、支付量按支付时间”可以共存于一次查询。
  2. 间接指标只做计算，不关心数据从哪来。比率、差值、求和、换算都可以用它表达。

二、过滤条件

条件支持等值、集合、存在、范围四种：

filter.go

这里有一个重要原则：条件不认识时不放宽。

Match 在条件非法时直接返回 false，而不是跳过条件。统计查询宁可少返回，也不能因为条件写错而返回全量数据。

三、路径取值

过滤条件里的字段支持点号路径，比如 order.status：

lookup.go

四、注册表与依赖解析

注册表保存所有指标，并负责把请求的指标名解析成“直接指标 + 按顺序排列的间接指标”。

registry.go

请求 客单价 时，会先解析出 营收、支付量，再把 客单价 放到最后计算；如果依赖成环，直接报错。

五、查询规格与后端

引擎不直接拼查询语句，而是把指标翻译成查询规格，交给后端执行：

backend.go

生产环境换后端时，只需要把 Spec 翻译成真实的查询，返回同样的 map[string][]Bucket。指标定义和引擎不用改。

六、引擎：合并时间桶，再算间接指标

Engine.Evaluate 是整个库的核心，顺序不能乱：

  1. 校验请求；
  2. 解析指标依赖；
  3. 把直接指标翻译成查询规格；
  4. 调后端拿每个指标的桶；
  5. 按时间 key 合并；
  6. 在合并后的值上计算间接指标。

engine.go

最容易写错的是顺序：间接指标必须在跨时间桶合并之后计算。

支付率这类指标，分子分母的时间字段可能不同。如果先在每个桶里除、再把比率平均，结果一定偏；正确做法是先合并分子分母，再做除法。

七、数值工具

比率和除法都要处理分母为零：

numbers.go

八、完整示例

下面这个 main.go 注册五个指标：下单量、支付量、营收、支付率、客单价。

cmd/demo/main.go

十、离生产化还差什么

这个库是完整可运行的骨架，上生产还需要补几块：

查询后端。 内存后端只做演示，真实后端要把 Spec 翻译成搜索请求：全局条件、指标过滤、时间范围、日期直方图、聚合。

多时间字段。 真实查询里，不同时间字段要分开建桶，再在结果层合并；引擎已经按指标时间字段分开处理。

缓存。 只缓存纯聚合结果，缓存键包含指标、时间、过滤、粒度；并发相同请求要合并。

并发。 多个指标可以并行查询，但要控制并发度，避免压垮后端。

可观测性。 记录每次查询的指标数、时间字段数、聚合规模、耗时，慢查询要能定位到具体指标。

错误处理。 后端超时、部分指标失败、数据格式异常，都要有明确的降级策略，而不是整页报错。

十一、小结

一个指标操作库，核心就四件事：

把时间字段放进指标、把计算放到合并之后、把后端做成接口，口径就有了唯一的落点，测试也不再依赖真实集群。

代码不复杂，难的是约束：什么时候该拒绝、什么时候该返回零、什么时候必须报错。这些约束，才是统计平台“可信”的来源。
